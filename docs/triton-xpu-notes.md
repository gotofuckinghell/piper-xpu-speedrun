# Triton XPU: что говорит документация и как это применить к нашей задаче

Источник: репозиторий `intel/intel-xpu-backend-for-triton` (клон в
`<PROJECT>\repos\intel-xpu-backend-for-triton`), файлы `README.md`,
`.github/WINDOWS.md`, `python/tutorials/03a-matrix-multiplication-tensor-descriptor.py`,
`benchmarks/triton_kernels_benchmark/*`.

## 1. Поддерживаемая конфигурация на Windows

- Windows 11, Arc A/B-серия, свежий драйвер.
- Visual Studio 2022 с компонентами VC.Tools, Windows11SDK.22621, VC.CMake.
- Intel Deep Learning Essentials 2026.1 (`C:\Program Files (x86)\Intel\oneAPI`).
- **PyTorch и Triton собираются из исходников** этим тулчейном; pip-колёса не
  поддерживаются.
- Включённые длинные пути (`LongPathsEnabled=1`) и `git config core.longpaths true` —
  без этого checkout PyTorch падает на именах тестов длиннее 260 символов.
- Каждая сессия начинается с `setvars.bat`; линкер требует `/FORCE:MULTIPLE`.

Наш стенд отличается (Windows Server 2025, стоковые колёса) — поэтому и
получились 0,64-0,70x и падение max-autotune на `pass_fds`.

## 2. Правила быстрых ядер (из README и туториалов)

1. **Tensor Descriptors вместо арифметики указателей.** `tl.make_tensor_descriptor`
   с `base/shape/strides/block_shape`; компилятор сам делает bounds-check и
   планирует загрузки. На XPU это включает DPAS и 2D block IO.
2. **Только 2D-дескрипторы, последний stride = 1.** Дескрипторы до 5D, но
   оптимизируются лишь 2D; для 3D+ переописывать блок как 2D.
3. **Порядок осей грида.** На XPU первая ось меняется быстрее: индекс тайла на
   `axis=0`, батч/эксперт — на `axis=1+`. Перепутать — потерять до 2x.
4. **Автотюн.** `triton.autotune` по `BLOCK_SIZE_*`, `num_warps`, `num_stages`,
   `grf_mode`; готовые сетки — в `benchmarks/triton_kernels_benchmark/`.
5. **Аннотации типов обязательны**, особенно для `tl.dot` без дескрипторов.
6. **Замер** — `triton.testing.do_bench`; профилирование ядер —
   `TRITON_XPU_PROFILE=1` + VTune, сквозное — `torch.profiler`.
7. Дескрипторы бывают device-side (внутри ядра, гибче) и host-side (при переносе
   кода с CUDA).

## 3. Что это значит для VITS

Горячая точка по трейсу: `aten::convolution_backward_overrideable` — 25,7 % CPU,
то есть обратный проход свёрток идёт медленным путём.

Кандидаты на своё ядро, по убыванию отдачи:

1. **dgrad для Conv1d с stride 1** (постнет, декодер): математически это
   корреляция входа с перевёрнутым ядром, раскладывается в GEMM
   `(C_out) x (C_in*k) @ (C_in*k) x L`. 2D-дескриптор по (L, C_in*k), ядро
   перевёрнутое — читается как обычная матрица. Это самый близкий к туториалу
   03a случай.
2. **Conv1d со stride 2** (энкодер дискриминатора): тот же GEMM, но с выборкой
   каждого второго столбца — блок-загрузка с шагом, дескриптор с stride 2 по L
   (последний stride тогда не 1 — придётся грузить блок и маскировать).
3. **Transposed conv в декодере**: формально тоже GEMM, но с разбросом вкладов;
   писать после того, как заработает пункт 1.

## 4. План проверки (без риска для обучения)

1. Снять реальные формы с шага обучения (C_in, C_out, k, L, stride) из трейса.
2. Написать стенд: eager-свёртка против Triton-ядра на этих формах,
   сравнение значений (allclose) и времени (`do_bench`).
3. Если выигрыш есть — оформить `torch.autograd.Function` с ручным backward и
   подменить только в дискриминаторе (там формы фиксированные: сегмент 2048).
4. Мерить полный шаг обучения, а не только ядро: индуктор уже показал, что
   локальное ускорение легко съедается накладными расходами.

## 5. Ограничения, которые надо держать в голове

- Сборка из исходников — часы, и наш хост формально не в списке поддерживаемых
  (Windows Server 2025 вместо Windows 11).
- `max-autotune` на стоковых колёсах падает (`pass_fds`), поэтому проверять
  выигрыш можно только после сборки.
- Для свёрток в репозитории готовых ядер нет: только GEMM/attention/softmax.
